3. System Overview

Three modules with a strict one-way dependency javafx-ui → guess-market-engine → guess-market-dto, enforced by module-info. The UI never touches a domain object: it calls the MarketEngine interface with flat immutable DTOs, renders the DTOs it gets back, and re-reads everything whenever the engine publishes a "data changed" event.

3.1 Modules

3.2 guess-market-dto

Every DTO is a flat, immutable record. A summary DTO (EventDTO, UserDTO) is what tables show and what the UI passes back as a command argument; a detail DTO embeds its summary DTO plus the heavy lists. EventDTO and UserDTO never reference each other — they cross-link by id / name.

3.3 guess-market-engine

MarketEngineImpl owns no rules: it resolves the DTO to a domain object via MarketCatalog, tells the Event aggregate root to do the work (every trading and lifecycle rule lives there), runs the result through a *Mapper and fires MarketEventPublisher. TradingMethod is the single polymorphic seam for LMSR-vs-Order-Book behaviour (callers never switch on its type). Money moves only through Account, which also keeps the append-only balance-over-time ledger. XML load and Java-serialization restore are the only two ways a whole market graph enters the catalog.

3.4 javafx-ui

GuessMarketApp boots one MarketEngineImpl and the main window; MainController injects that engine into the two tab controllers, which register as MarketDataChangeListeners. All bonuses live in ui.common.

4. Key Design Choices & Assumptions

  • Layering. Three modules with module-info declarations; the UI sees only engine.api + the DTOs. The engine's model, lmsr, xml, mapper, serialization packages are not exported.
  • Immutable DTOs. The engine never leaks a mutable entity; the UI can't accidentally mutate market state.
  • Event is the aggregate root. No plain setters; every rule about options, money, holdings and lifecycle is enforced inside it. MarketEngineImpl is a thin facade.
  • Money is confined to Account (as double dollars). Every debit/credit appends a LedgerEntry that records the resulting balance, which is what the balance-over-time chart reads directly.
  • Order Book has no escrow. Cash and shares move only when an order actually fills. A placed order is checked against the placer's current balance / free shares (a bid needs the full cost incl. on-purchase commission; an ask needs the shares net of the user's own other asks). Price is capped at d − 0.01.
  • Blocked users (negative-balance rule). A user cannot normally go negative. But a resting bid can become unhonourable if its owner has since spent that money on another order. When that fill happens we do honour it: the owner's balance is forced negative, they are blocked (the engine refuses every subsequent action of theirs), a dialog notifies the checker, and a red banner marks the user. There is no way to top the account back up (per the spec). If instead the seller of a resting ask can no longer deliver the shares, that order is simply dropped.
  • Filters. The three event filters are combo boxes, each with an explicit "All" option selected by default (a pragmatic reading of the "toggle buttons" hint — one control, clearly shows the active choice).
  • Loading. File-chooser dialog only. Parsing runs on a JavaFX Task with a progress bar; since parsing is near-instant, a ~1.3 s paced delay is added so the indicator is visible. All the Exercise-1 input validations still apply, plus the Exercise-2 user checks.
  • Closed events. The event drill-in shows the winning option and total shares bought per option. A user's per-event view shows their shares per option and, once closed, the winner and their net cash result on that event (summed from the ledger).
  • Binary events. Exactly two options per event, as in the schema.
  • Created events get the next free integer id (max existing + 1). Before creation the engine checks the chosen market maker can afford the trading-method subsidy; if not, an error dialog explains why. A created event starts NOT_ACTIVE — the creator activates it like any other.
  • Resize. The window is resizable; content sits in scroll panes and split panes and a minimum window size stops controls being clipped.
  • State save/load (Exercise-1 bonus) writes/reads the full object graph with Java serialization and is offered from the File menu, separate from XML loading.

5. Tests

The engine module carries a JUnit 5 suite (run from IntelliJ) covering the LMSR maths, XML validation, the full Order-Book lifecycle (matching, minting, market buys, settlement), state round-trips, the balance ledger, event creation, and the blocked-user path. The UI is exercised manually against the course test files.
